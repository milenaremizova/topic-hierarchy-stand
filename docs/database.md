# База данных

Postgres + Drizzle ORM. Здесь всё, что нужно, чтобы создать базу и работать с ней.

## 1. Запустить Postgres

Есть три варианта, код стенда от выбора не меняется — меняется только `DATABASE_URL`.

### Вариант А: локально без установки (для разработки)

```bash
npm run db:local
```

Это **PGlite** — настоящий Postgres 18, собранный в WebAssembly. Ставится как
обычный npm-пакет вместе с проектом, поэтому ничего устанавливать в систему
не нужно. Слушает `localhost:5432`, как обычный Postgres, данные хранит
в папке `data/pgdata` (она в `.gitignore`).

Оставь этот терминал открытым — это твой сервер БД. Во втором терминале
запускай `npm run dev`. Остановить — Ctrl+C.

В `.env`:

```
DATABASE_URL=postgres://postgres@localhost:5432/postgres
```

Чем отличается от обычного Postgres — важно знать:

- **Одна база** `postgres` и **пароли не проверяются**. Поэтому для локальной
  разработки шаги с `CREATE ROLE` / `CREATE DATABASE` не нужны.
- **Один процесс на папку.** Не запускай `db:local` дважды — две копии
  на одной папке испортят данные.
- Несколько подключений (сервер + pgAdmin) работают через мультиплексор:
  для разработки хватает, но под нагрузку это не рассчитано.
- Начать с чистой базы: остановить `db:local`, удалить `data/pgdata`.

### Вариант Б: настоящий Postgres (на сервере или когда появится свой)

Приложению нужна **своя роль**, а не суперпользователь `postgres`.
Принцип минимальных прав: если в коде будет дыра, через неё не получится
удалить чужие базы или создать новых пользователей.

**Только не на продовом сервере** — стенду нужен отдельный.

Подключись суперпользователем и выполни:

```sql
-- Роль, под которой работает стенд. LOGIN — может подключаться
CREATE ROLE stand LOGIN PASSWORD 'придумай-пароль';

-- База, владелец — эта роль. Владелец может создавать в ней таблицы,
-- поэтому миграции пройдут без дополнительных GRANT
CREATE DATABASE stand OWNER stand;
```

В pgAdmin то же самое мышкой: Login/Group Roles → Create (вкладка Privileges →
Can login), потом Databases → Create с Owner = stand.

Проверка: подключиться новой ролью к новой базе.

```bash
psql "postgres://stand:придумай-пароль@localhost:5432/stand" -c "select current_user, current_database();"
```

Перед любыми командами проверяй, куда подключена:

```sql
SELECT inet_server_addr(), current_database(), current_user;
```

### Вариант В: через Docker

В `.env` заполни `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` и запусти:

```bash
docker compose up -d db
```

Контейнер сам создаст роль и базу при первом запуске. Данные хранятся в томе
`pgdata` и переживают перезапуск. Удалить всё и начать заново:
`docker compose down -v` (флаг `-v` удаляет том — данные пропадут).

## 2. Строка подключения

```
postgres://stand:пароль@localhost:5432/stand
           └─┬─┘ └─┬──┘ └───┬───┘ └┬─┘ └─┬─┘
         роль   пароль   хост  порт  база
```

Кладётся в `.env` как `DATABASE_URL`. Если в пароле есть `@`, `:`, `/`, `#` —
их нужно закодировать (`@` → `%40`) или выбрать пароль без них.

## 3. Создать таблицы

```bash
npm run db:migrate    # применить миграции
npm run db:seed       # + создать первого руководителя (миграции применит сам)
```

Сервер при старте тоже применяет миграции, так что отдельно это нужно
только в первый раз или для проверки.

## 4. Как устроены миграции

```
schema.ts  ──npm run db:generate──▶  drizzle/0001_….sql  ──старт сервера──▶  база
(как должно быть)                    (как туда дойти)                       (как есть)
```

1. Меняешь `apps/api/src/db/schema.ts`.
2. `npm run db:generate` — Drizzle сравнивает схему с прошлым снимком
   (`drizzle/meta/`) и пишет SQL.
3. **Читаешь SQL.** Особенно если видишь `DROP` — генератор мог понять
   переименование как «удалить и создать заново», а это потеря данных.
4. Перезапускаешь сервер — миграция применяется.
5. Коммитишь `schema.ts` и папку `drizzle/` вместе.

Какие миграции уже применены, Drizzle помнит в таблице
`drizzle.__drizzle_migrations` (отдельная схема `drizzle`).

**Правила:**

- Применённую миграцию не редактируют и не удаляют — только новая поверх.
- Файлы в `drizzle/meta/` руками не трогают.
- Пока стенд не запущен в бою и данные не жалко, можно снести базу
  и папку `drizzle/` и сгенерировать всё заново одной миграцией.

## 5. Наши таблицы

```
accounts ──< sessions
    │
    └──< chat_runs ──< hierarchy_events
```

| Таблица            | Что хранит                                                |
| ------------------ | --------------------------------------------------------- |
| `accounts`         | Учётки: логин, хеш пароля, роль, ФИО на стенде, группа    |
| `sessions`         | Активные входы: токен из cookie и срок действия           |
| `chat_runs`        | Прохождение одного диалога одним оператором               |
| `hierarchy_events` | Каждое действие при выборе тематики — сырьё для аналитики |

Что используется из возможностей Postgres:

- **`uuid`** — первичные ключи. Генерируются в коде (`randomUUID()`), поэтому
  id известен ещё до вставки.
- **`ENUM`-типы** (`role`, `test_group`, `run_status`, `hierarchy_event_type`) —
  база не даст записать значение не из списка. Добавить значение потом:
  поменять список в схеме и сгенерировать миграцию (`ALTER TYPE … ADD VALUE`).
- **`timestamptz`** — время с часовым поясом. В коде это `Date`.
- **`jsonb`** — снимок пути тематики. Можно делать запросы внутрь:
  `final_path->-1->>'name'` — название последнего элемента.
- **`ON DELETE CASCADE`** — удалили учётку → удалились её сессии,
  прохождения и их события.
- **Индексы** — под конкретные частые запросы: события одного прохождения
  по времени, прохождения одной учётки по порядку.

## 6. Полезные запросы

```sql
-- Учётки и сколько диалогов пройдено
SELECT a.login, a.display_name, a.test_group,
       count(r.id) FILTER (WHERE r.status = 'closed') AS done
FROM accounts a
LEFT JOIN chat_runs r ON r.account_id = a.id AND NOT r.archived
WHERE a.role = 'operator'
GROUP BY a.id
ORDER BY a.login;

-- Траектория одного прохождения
SELECT ts, type, node_id, query, results_count
FROM hierarchy_events
WHERE run_id = '…'
ORDER BY ts;

-- Посмотреть, что за миграции применены
SELECT * FROM drizzle.__drizzle_migrations;
```

## 7. Чем смотреть

- **pgAdmin / DBeaver** — Register → Server, данные из `DATABASE_URL`.
  Для `db:local`: Host `localhost`, Port `5432`, Username `postgres`, пароль пустой.
  Если pgAdmin старый и ругается на версию сервера (PGlite — это Postgres 18),
  смотри через Drizzle Studio.
- **Drizzle Studio** — `cd apps/api && npx drizzle-kit studio`,
  откроет веб-интерфейс с таблицами нашей схемы.
- **psql**, если есть: `psql "$DATABASE_URL"`.

## 8. Бэкап

```bash
# Сохранить
pg_dump "$DATABASE_URL" -Fc -f stand-$(date +%F).dump
# Восстановить в пустую базу
pg_restore -d "$DATABASE_URL" --no-owner stand-2026-11-20.dump
```

В Docker: `docker compose exec db pg_dump -U stand -Fc stand > stand.dump`.

Для `db:local`: остановить его и скопировать папку `data/pgdata`.
